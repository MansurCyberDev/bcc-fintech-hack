D-32 🟡 Неоднозначный термин и противоречие по времени доставки

Незначительно · Однозначность (ISO 29148 5.2.5 c; IEEE 830 4.3.2) · требования: R-01 · найдено: LLM

«Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.» — строка 21

Почему это дефект. Термин «личный бюджет» не определен в понятийном аппарате документа (далее используется «месячный порог расходов»). Фраза «в момент покупки» противоречит НФТ (R-10), допускающему задержку отправки push до 1 минуты.

Как исправить. Заменить «личного бюджета» на «установленного месячного порога расходов по карте», а «в момент покупки» на «в течение 1 минуты после проведения покупки».

Вопрос автору. Какое точно время доставки уведомления считается допустимым с точки зрения бизнеса?

D-08 🟠 Неполная архитектурная схема связей компонентов

Существенно · Полнота (ISO 29148 5.2.5 d; IEEE 830 4.3.3) · требования: R-02 · найдено: LLM

«Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.» — строка 25

Почему это дефект. В текстовой цепочке архитектуры отсутствует связь между сервисом настроек и сервисом учета расходов, хотя для проверки порога сервис учета расходов должен запрашивать данные из сервиса настроек.

Как исправить. Добавить связку «Сервис учета расходов ↔ сервис настроек» в описание архитектурной цепочки.

Q-01. 🚫 Каким HTTP-методом и с какой структурой запроса должна выполняться операция сохранения порога (/alerts/saveLimit)?

  1. POST с JSON-телом запроса
  2. PUT с JSON-телом запроса
  3. GET с query-параметрами без тела

Q-02. 🚫 Каким образом сервис должен возвращать результаты выполнения и статус бизнес-ошибок клиенту?

Кому: Разработчик API · дефекты: D-04, D-20, D-21, D-23, D-24, D-25, D-42, D-43, D-45 · требования: R-40, R-38, R-39, R-44, R-23, R-30, R-34, R-45, R-48

Зачем: Противоречие между возвратом HTTP 200 OK с result=ERROR и стандартными кодами 4xx/5xx приведет к некорректной обработке ошибок клиентом.

  1. Возвращать HTTP 400/422 со структурой ошибки при невалидных данных и HTTP 200/201 при успехе
  2. Всегда возвращать HTTP 200 OK с полем result (OK / ERROR) в теле ответа

Q-03. 🚫 По какой дате следует относить операцию покупки к расходам месяца и что происходит с лимитом при возвратах?

Кому: Аналитик · дефекты: D-01, D-11 · требования: R-15, R-06

Зачем: Разночтения между датой покупки и датой проведения операции вызовут ошибочный расчёт остатка бюджета и неверные push-уведомления.

  1. Расчёт по дате совершения операции (Transaction date), возврат уменьшает расходы без сброса флага push
  2. Расчёт по дате финансового проведения (Posting date), возврат сбрасывает флаг отправленного push
  3. Расчёт по дате совершения, возврат уменьшает расходы и сбрасывает флаг push за тот месяц

Q-04. 🚫 В каких единой валютной единице должны храниться и передаваться в API суммы порогов и операций?

Кому: Разработчик API · дефекты: D-05 · требования: R-03, R-12, R-18

Зачем: Смешивание тиынов и тенге в хранилище и API приведет к ошибкам в расчете сумм на 2 порядка.

  1. Всё хранить и передавать строго в тиынах (целое число)
  2. Всё хранить и передавать строго в тенге (целое число)
  3. Хранить в тиынах, но в API передавать и принимать в тенге

Q-05. 🚫 Сбрасывается ли лимит 'максимум 1 push в месяц' при изменении или переустановке порога клиентом?

Кому: Product owner · дефекты: D-06, D-13 · требования: R-07, R-08, R-05

Зачем: Отсутствие единого правила не позволяет запрограммировать и протестировать условие генерации уведомления.

  1. Да, смена порога сбрасывает ограничение и позволяет получить повторный push в этом же месяце
  2. Нет, ограничение 1 push в календарный месяц действует строго независимо от смены настроек

Q-06. 🚫 Кто и когда заполнит отсутствующие разделы спецификации (R-13, версию, дату и блок согласования)?

  1. Аналитик заполнит до старта спринта разработки
  2. Тестировщики заполнят раздел R-13 при написании тест-кейсов
  3. Product owner согласует текущую версию без заполнения R-13

Q-07. Какой HTTP-код ответа должен возвращаться при запросе операции по чужой или несуществующей карте?

  1. Возвращать 404 Not Found во всех случаях (скрывать существование чужой карты)
  2. Возвращать 403 Forbidden для чужой карты и 404 Not Found для отсутствующей

Q-08. Какие типы данных должны быть строго закреплены за параметрами amount и enabled в спецификации API?

  2. amount: integer (32 bit), enabled: boolean (true/false)
  3. amount: string, enabled: string

Приложение Б. Замечания, отклонённые критиком

Эти замечания модель-аналитик предложила, но независимый критик счёл их ложными. Приведены для прозрачности.

  • Нарушение семантики HTTP в дочерней спецификации API (R-12) — причина: Дублирует замечание L-08, в котором приведены более точные цитаты непосредственной спецификации API.
  • Использование HTTP GET для модификации данных (R-25) — причина: Дублирует замечание L-08 о нарушении HTTP-семантики при использовании метода GET для сохранения настроек.
  • Не определено поведение при снижении порога ниже текущих расходов (R-26) — причина: Дублирует замечание L-15 о неопределённости логики при снижении порога ниже текущих расходов.
  • Неоднозначность разделения ошибок между кодами 400 и 200 (R-39) — причина: Дублирует замечание L-25 и L-23 в части нечеткости разграничения ответов 400 и 200 ERROR.

  • Неполное описание условий и структуры ответа ошибки 500 (R-43) — причина: Пожелание о наличии traceId/correlationId является детализацией реализации и не противоречит требованиям.
