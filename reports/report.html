D-01 🔴 Метод GET для операции изменения данных

Критично · Корректность (ISO 29148 5.2.5 h; IEEE 830 4.3.1) · требования: R-18, R-03 · найдено: правило + LLM

«REST type | GET» — строка 104 «Description | Сохранение порога. Функциональные требования: чтение порога» — строка 103 «CURL | curl -G "$BASE/alerts/saveLimit" -H "Authorization: Bearer $TOKEN" --data 'cardId=demo-42&amount=50000&enabled=1'» — строка 109 «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить».» — строка 29

Почему это дефект. Операция меняет состояние (сохранение/замена настройки), но описана как GET. GET по RFC 9110 должен быть безопасным и идемпотентным: его кэшируют, повторяют, логируют вместе с параметрами в URL. Это ошибка проектирования и риск ИБ.

Как исправить. Использовать PUT (замена настройки) или POST, параметры передавать в теле JSON.

Вопрос автору. Метод изменяет данные или только читает их? Если изменяет — согласны ли заменить GET на POST/PUT с телом запроса?

D-07 🟠 Отсутствуют тексты и условия ошибок UI

Существенно · Полнота (ISO 29148 5.2.5 d; IEEE 830 4.3.3) · требования: R-03 · найдено: LLM

«При ошибке ввода сообщение появляется под полем.» — строка 29

Почему это дефект. Требование указывает на появление сообщения при ошибке ввода, но не специфицирует конкретные тексты ошибок и правила активности кнопки «Сохранить».

Как исправить. Описать конкретные тексты ошибок для всех валидационных правил и состояние кнопки «Сохранить» при некорректном вводе.

Приложение Б. Замечания, отклонённые критиком

Эти замечания модель-аналитик предложила, но независимый критик счёл их ложными. Приведены для прозрачности.

  • Нарушение HTTP-семантики при ошибке валидации (R-23) — причина: Дубликат замечания L-06, в котором проблема возврата HTTP 200 со статусом ERROR раскрыта наиболее полно со ссылками на обе стороны.
  • Возврат ошибки ERROR со статусом HTTP 200 (R-35) — причина: Дубликат замечания L-06, объединяющего противоречие HTTP 200 OK result ERROR и описания статуса 400.
  • Противоречие в обработке неверных параметров (R-40) — причина: Дубликат замечания L-06, которое точнее формулирует противоречие статуса 400 и ответа 200 с result: ERROR.
  • Неопределённость понятия «в момент покупки» (R-01) — причина: Проблема надумана: бизнес-цель дает верхнеуровневый контекст, а точные временные рамки (в течение минуты) регламентированы в НФТ.
  • Неполное описание архитектурных связей (R-02) — причина: Запрос деталей реализации: общая архитектурная схема дает концептуальный контекст, а детальные протоколы API специфицированы в Части B.
  • Неопределенная точка отсчета времени отправки push (R-10) — причина: Проблема надумана: требование четко формулирует точку отсчета («после получения события») и ограничение по времени («в течение минуты»).
  • Неполная спецификация модели данных (R-11) — причина: Требование деталей реализации: спецификация определяет необходимый состав хранимых сущностей, а структура таблиц проектируется разработкой.
  • Неполнота условия: отсутствуют числовые значения границ (R-24) — причина: В документе есть ответ: числовые значения порогов (1 000–1 000 000 ₸) явно указаны в требовании Ф-1 и в таблице Query-параметров.
  • Не описан сценарий превышения сниженного порога (R-26) — причина: Дубликат замечания L-08, в котором неполнота описания логики при снижении порога описана точнее и подробнее.
  • Отсутствует заголовок Content-Type и идентификатор карты в ответе (R-41) — причина: Чистый вкус и придирка: формат ответа специфицирован JSON-структурой, а заголовок Content-Type и возвращение cardId в ответе не требуются.
  • Противоречие в описании статуса 403 (R-43) — причина: Дубликат замечания L-18, описывающего нестыковку между описанием 403 Forbidden и фактическим возвратом 404.
  • Объединение двух независимых проверок в один шаг (R-21) — причина: Чистый вкус: объединение двух валидаций в одном шаге алгоритма является стилистическим решением и не влияет на разработку и тестирование.
  • На схеме не отражена проверка авторизации и прав (R-27) — причина: Проблема надумана: текстовая схема иллюстрирует верхнеуровневый поток данных, а шаги авторизации детализированы в алгоритме метода.
  • Избыточный подраздел 403 при отсутствии сценария (R-47) — причина: Дубликат замечания L-18, указывающего на проблемы в оформлении и содержании раздела 403/404.
