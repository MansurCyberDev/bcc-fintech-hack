Проверь документ как НАБОР требований по критериям набора: set_complete, consistent, set_feasible, comprehensible, validatable, ranked, modifiable, traceable.

Работай по шагам, это самое ценное в проверке набора:

1. **Примеры и критерии приёмки против правил.** Для КАЖДОГО примера, сценария и строки критериев приёмки примени бизнес-правила документа буквально и вычисли, какой результат из них следует. Если ожидаемый результат в примере другой — это противоречие (consistent, critical). Обращай внимание на границы периодов, даты и время, часовые поясы, округление, единицы.
2. **Правила против правил.** Найди пары правил про одну и ту же сущность, счётчик, лимит, флаг или статус. Придумай сценарий, где действуют оба правила, и проверь, не требуют ли они разного (одно запрещает, другое требует; одно сбрасывает, другое сохраняет). Нашёл — противоречие (consistent).
3. **Бизнес-часть против API и данных.** Всё, что пользователь видит или делает (экран, поле, действие), должно иметь операцию API и данные, из которых это берётся. Есть «читает и сохраняет», а описана только запись — пропущена операция (set_complete). Сверь коды ответов, типы и единицы между частями.
4. **Пропущенные сценарии.** Повторная доставка и порядок событий (по какому ключу дедуплицировать), одновременные операции, состояния сущности (заблокирована, перевыпущена, выключено, изменено), ошибки внешних систем, безопасность (персональные данные в URL, права доступа), откат.
5. **Проверяемость набора.** Какие правила не покрыты ни одним критерием приёмки.

Сначала противоречия (шаги 1–2), они важнее всего. Для противоречия приведи обе цитаты. Не придумывай дефекты, которых нет: каждое замечание должно опираться на дословные цитаты.
