# AI Requirements Validator

ИИ-агент, который проводит **статическое ревью документа с требованиями до начала разработки**: нарезает документ на отдельные требования, проверяет каждое и весь набор по ISO/IEC/IEEE 29148:2018 (п. 5.2.5–5.2.6) и IEEE Std 830-1998 (п. 4.3), **подтверждает каждую цитату кодом**, задаёт автору **уточняющие вопросы** и пишет отчёт на русском.

Команда хакатона **BCC-HUB x MNU FinTech Hackathon** — https://bcchubagents.mnu.kz/ · Задание: https://github.com/BCC-HUB/ai-requirements-validator-task

## Быстрый старт (3 шага)

```bash
# 1. Установить зависимости (Python 3.10+)
pip install -r requirements.txt

# 2. Положить ключ LLM
cp .env.example .env          # Windows: copy .env.example .env
# откройте .env и впишите GEMINI_API_KEY=ваш_ключ

# 3. Запустить проверку одной командой: <документ> <отчёт>
python main.py docs/requirements.md reports/report.md
```

Отчёт появится в `reports/report.md`, рядом — `reports/report.html` (удобно открыть в браузере) и `reports/report.json` (для машинной обработки).

## Как получить ключ LLM

1. Откройте https://aistudio.google.com/apikey и войдите в Google-аккаунт.
2. Нажмите **Create API key** — ключ бесплатный (тариф Free достаточен для хакатона).
3. Скопируйте ключ в файл `.env` в корне репозитория: `GEMINI_API_KEY=...`

Модель по умолчанию — **`gemini-2.5-flash`** (Google Gemini API). Сменить модель: `GEMINI_MODEL=...` в `.env`. Посмотреть модели, доступные по вашему ключу: `python main.py --list-models`.

Можно использовать любую OpenAI-совместимую модель (OpenAI, OpenRouter, Groq, локальный Ollama): в `.env` укажите `LLM_PROVIDER=openai`, `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL`.

> `.env` перечислен в `.gitignore` — ключ не попадёт в репозиторий. Никогда не коммитьте ключи.

## Команды

| Команда | Что делает |
| :--- | :--- |
| `python main.py docs/requirements.md reports/report.md` | Полная проверка (LLM + правила + критик) |
| `python main.py doc.pdf reports/report.md` | То же для PDF (поддерживаются `.md`, `.pdf`, `.docx`, `.txt`) |
| `python main.py doc.md reports/report.md -i` | **Интерактивный режим**: агент задаёт уточняющие вопросы в терминале и учитывает ответы |
| `python main.py doc.md reports/report.md --answers answers.json` | Ответы автора из файла `{"Q-01": "ответ", ...}` |
| `python main.py doc.md reports/report.md --offline` | Без LLM, только правила (работает без ключа и интернета) |
| `python main.py doc.md reports/report.html` | Основной файл в HTML (рядом всё равно будет .md) |
| `python web.py` | Веб-интерфейс для демо: http://127.0.0.1:8000 |
| `python -m pytest` | Тесты (нужен `pip install -r requirements-dev.txt`) |

Флаги: `--no-critic` (минус 1 запрос к LLM), `--no-html`, `--no-json`, `-v` (подробный лог).

## Что в отчёте

1. **Паспорт прогона** — документ, дата, модель, версия агента (git-коммит), режим, число вызовов LLM, сколько замечаний LLM отброшено из-за неподтверждённой цитаты.
2. **Как агент нарезал требования** — таблица «ID в отчёте — ID в документе — краткая формулировка (цитата) — место (строки)».
3. **Проверка каждого требования** — матрица «требование × 9 критериев ISO 29148» и разбор каждого дефекта: цитата + строка, почему это дефект, как исправить, вопрос автору.
4. **Проверка всего набора** — полнота, непротиворечивость, реализуемость, понятность, валидируемость, ранжирование, модифицируемость, трассируемость.
5. **Уточняющие вопросы автору** — сгруппированы, с вариантами ответа, адресатом и пометкой «блокирующий».
6. **Сводка** — число требований, нарушений, список критичных дефектов.
7. **Итог** — можно ли начинать разработку и тестирование, что исправить в первую очередь.

## Как это работает

```
документ ─► 1. Чтение (.md/.pdf/.docx) ─► 2. Нарезка на требования (код)
        ─► 3. Правила (код): размытые слова, заглушки, HTTP-семантика, типы, единицы, границы, версия…
        ─► 4. LLM-аналитик: каждое требование (пачками) + весь набор
        ─► 5. Проверка цитат КОДОМ ─► слияние дублей ─► LLM-критик отсеивает ложные срабатывания
        ─► 6. LLM-уточнитель: вопросы автору (+ применение ответов)
        ─► 7. Вердикт и отчёт (.md / .html / .json)
```

Ключевые идеи:
- **Ноль выдуманных цитат.** Замечание LLM попадает в отчёт, только если код нашёл его цитату в документе.
- **Гибрид правил и LLM.** Формальные дефекты находят детерминированные правила (одинаково при каждом прогоне), смысловые — LLM.
- **Без LLM тоже работает.** Если ключа нет или API недоступен, агент выдаёт отчёт по правилам и честно пишет об этом в паспорте.
- **Без подгонки.** Правила и промпты общие, в них нет ответов для конкретного документа.

Подробнее: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Структура

```
main.py              CLI: python main.py <документ> <отчёт>
web.py               веб-интерфейс для демо (стандартная библиотека)
src/
  ingest.py          чтение .md/.pdf/.docx/.txt
  split.py           нарезка на требования (с номерами строк)
  checks/rules.py    детерминированные правила
  checks/llm_checks.py  проверки LLM (требования, набор)
  checks/critic.py   критик: отсев ложных срабатываний
  verify.py          проверка цитат кодом
  clarify.py         уточняющие вопросы и ответы автора
  pipeline.py        оркестратор этапов, вердикт
  llm/client.py      клиент Gemini / OpenAI-совместимых API (повторы, лимиты, JSON)
  report/            Markdown, HTML, JSON
prompts/             промпты (system, проверка требований/набора, критик, вопросы)
docs/                входной документ организаторов + документация проекта
reports/             отчёты, сформированные агентом
tests/               тесты (pytest), включая полный прогон с поддельной LLM
```

## Как работаем в команде
1. `main` всегда рабочий — напрямую в него не пушим.
2. Перед работой: `git pull origin main`, своя ветка: `git checkout -b feature/название`.
3. Pull Request в `main`, кто-то из команды смотрит и мёржит.
4. Ключи — только в `.env`.
